# 面试题：你项目怎么管理依赖？

## 一、核心答案（30 秒版）

我项目用 **`.venv` 虚拟环境**做**依赖隔离**，每个项目有独立的 Python 解释器和包目录，
避免和系统 Python 或其他项目产生**依赖冲突**。依赖用 **`requirements.txt`** 声明并
**版本固定**，保证**环境可复现**。

### 包含的学术术语

| 术语 | 英文 | 作用 |
|------|------|------|
| 依赖隔离 | Dependency Isolation | 环境不互相污染 |
| 依赖冲突 | Dependency Conflict | 避免版本打架 |
| 版本固定 | Version Pinning | 锁死版本 |
| 环境可复现 | Reproducibility | 到哪都能跑 |

## 二、展开答案（面试官追问时用）

如果面试官问："能具体说说吗？"

具体分三个层面：

**第一，环境隔离**。我在项目根目录用 `python -m venv .venv` 创建虚拟环境，
每个项目一个独立的 Python 解释器和 `site-packages` 目录。这样项目 A 用
LangChain 0.3、项目 B 用 LangChain 0.1，互不影响。

**第二，依赖声明**。我用 `requirements.txt` 列出项目所需的所有第三方库，
并且用 `==` 精确固定版本号，比如 `langchain==0.3.7`。这样避免了上游依赖更新
引入的破坏性变更，保证今天能跑、明天也能跑。

**第三，可复现性**。别人克隆我的项目后，只要 `pip install -r requirements.txt`，
就能得到和我完全一致的环境。部署到服务器也一样。

## 三、结合项目的答案

我项目叫**企业知识库智能助手**，用 LangChain + LangGraph 做 RAG + Agent。

- **环境方面**：用 PyCharm 创建项目时自动生成了 `.venv`，我在里面装依赖。
- **依赖方面**：`requirements.txt` 里锁定了 15 个核心包，比如 `langchain==0.3.7`、
  `langgraph==0.2.45`、`qdrant-client==1.12.1`。因为 LangChain 生态更新很快，
  不锁版本，第二天可能就跑不起来了。
- **踩过的坑**：早期 `requirements.txt` 用记事本保存成了 GBK 编码，pip 读取时报
  `UnicodeDecodeError`，后来改成 UTF-8 就好了。这让我意识到**编码规范**也是依赖
  管理的一部分。

## 四、面试官可能追问的 5 个问题

### 追问 1：为什么要版本固定，不固定不行吗？

不固定有两个风险：**一是破坏性变更**，上游库升级 API 后，我的代码调用旧接口会报错；
**二是不可复现**，别人装出来的版本和我不同，可能出现"在我电脑能跑，在你电脑跑不了"。
所以我用 `==` 精确锁定。

### 追问 2：requirements.txt 和 poetry.lock 有什么区别？

`requirements.txt` 是**依赖声明**，我手写我要装什么。`poetry.lock` 是**锁文件**，
记录了完整的依赖树（包括间接依赖）和精确版本 + 哈希值。锁文件更严格，能保证 100% 复现。
我目前用 `requirements.txt` 足够了，如果项目依赖更复杂，我会考虑 Poetry。

### 追问 3：虚拟环境里都装了什么？

装了 RAG 全链路需要的库：
- LangChain、LangGraph（编排）
- qdrant-client（向量库）
- sentence-transformers（向量化）
- fastembed（BM25 稀疏向量）
- fastapi、uvicorn（接口服务）
- pdfminer.six（PDF 解析）
- python-dotenv（配置）

### 追问 4：如果依赖装不上怎么办？

- **网络问题**：加国内镜像 `-i https://pypi.tuna.tsinghua.edu.cn/simple`
- **版本冲突**：看报错，调整版本约束
- **依赖重**：像 `sentence-transformers` 依赖 PyTorch，先单独装 CPU 版 torch 再装它
- **系统缺编译工具**：装 VS Build Tools 或换预编译包

### 追问 5：你项目怎么部署到服务器？

服务器上先装 Python 和虚拟环境，然后 `git clone` 项目、
`pip install -r requirements.txt`、启动服务。如果用 Docker 部署，会在 Dockerfile 里
`COPY requirements.txt` 后 `RUN pip install -r requirements.txt`，把依赖装进镜像。

## 六、容易被扣分的说法

| ❌ 别说 | ✅ 应该 |
|--------|--------|
| 我直接 pip install，没用虚拟环境 | 用 .venv 隔离，避免污染系统 |
| requirements.txt 我随便写的 | 用 `==` 精确版本固定 |
| 我不太清楚版本冲突 | 避免破坏性变更，保证可复现 |
| pip freeze 导出的 | 手动维护核心依赖，更干净 |
| 没遇到过问题 | 遇到过编码问题，改成 UTF-8 |

## 七、加分项

| 加分点 | 说法 |
|-------|------|
| 提到锁文件 | 如果项目复杂，我会用 Poetry 管理，生成 lock 文件 |
| 提到 CI | CI 里也用 requirements.txt 安装，保证测试和生产环境一致 |
| 提到 Docker | Dockerfile 里也 COPY requirements.txt 装依赖，环境和本地一致 |
| 提到安全 | 依赖不提交 .venv，只提交 requirements.txt，减小仓库体积 |
| 提到许可证 | 选依赖时看许可证，避免商用限制 |
